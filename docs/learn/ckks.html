The running example, shared by every lesson

One neuron of an LLM

A user types a private prompt. After tokenization, one token becomes a tiny embedding x. The server owns one neuron of the model: weights w and bias b. The neuron computes

y = ReLU( w₁·x₁ + w₂·x₂ + b )

This is the smallest piece of a Transformer that still has both kinds of work: a linear part (multiply and sum, like every matrix product in attention and the feed-forward layers) and a non-linear part (ReLU, standing in for GELU, SiLU and Softmax). The server must compute y without ever seeing x or y.

client

Make keys

CKKS works with polynomials. Here the ring has degree N = 4, so every polynomial has 4 integer coefficients, and all arithmetic wraps around with X⁴ = −1. The secret key s is a polynomial with tiny coefficients in {−1, 0, 1}.

s(X) = …

The client also publishes a public key and two evaluation keys that let the server do work on ciphertexts: a relinearization key (needed after ciphertext × ciphertext) and a rotation key (needed to move values between slots). They are encryptions of s², and of s with its slots rotated, so they reveal nothing.

Toy sizes. N = 4 is wildly insecure. Real LLM deployments use N = 65,536 and a modulus of about 1,500 bits. The algebra is identical, which is why a 4-coefficient version teaches the real thing.

client

Encode: numbers become a polynomial

A degree-4 polynomial holds N/2 = 2 slots. CKKS multiplies the inputs by a scale Δ = 2²⁰ to keep about 6 decimal digits, then finds the polynomial whose values at two special complex points are exactly those slots. Every later operation on the polynomial acts on both slots at once: this is SIMD packing, the reason CKKS suits large matrix products.

Encrypt: hide the polynomial under noise

A ciphertext is a pair of polynomials (c₀, c₁) with huge coefficients modulo q. It is built so that one simple combination with the secret key gives back the message plus a small random error e:

c₀ + c₁ · s ≡ Δ·m + e (mod q)

4

server

Multiply by the weights, then rescale

The server encodes its own weights w = [0.5, −0.25] the same way (they stay unencrypted) and multiplies both ciphertext polynomials by them. Because encoding respects multiplication, both slots are multiplied at once: slot-wise x ⊙ w.

(c₀, c₁) × w → decrypts to Δ²·(x ⊙ w) + small error

The scale is now Δ², 40 bits. Rescaling divides the whole ciphertext by Δ to bring the scale back to Δ. That throws away 20 bits of the modulus. This is one level, and the budget is finite.

5

server

Rotate and add: the sum w₁x₁ + w₂x₂

The two products sit in different slots, and CKKS can only add slot 1 to slot 1. To sum them, the server rotates a copy so the slots swap places. Rotation substitutes X → X⁵ in both polynomials, which secretly changes the key, then key switching with the rotation key brings it back under s. Adding the copy gives the dot product in every slot.

Finally the server adds the bias b = 0.1, encoded at the current scale. Addition is cheap and uses no level.

ReLU: replace it with a polynomial

CKKS can only add and multiply. ReLU(z) = max(0, z) is neither, so the server evaluates a polynomial that looks like ReLU on a chosen interval. Here we use the best degree-2 fit on [−1, 1]:

ReLU(z) ≈ p(z) = 0.09375 + 0.5·z + 0.46875·z²

Evaluating p(z) takes two multiplications in a row. z · z multiplies two ciphertexts, which produces a third polynomial. Relinearization with the relinearization key folds it back into a pair. Then comes the multiplication by 0.46875. Each one costs a rescale, so the ciphertext ends at the bottom level.

Out of levels. One more layer would need bootstrapping: homomorphically re-running decryption to refill the modulus. In real CKKS LLM inference, bootstrapping takes 50–75% of the total time (SoK, §4.2.1).

Decrypt and decode

The server sends the final ciphertext back. The client computes c₀ + c₁·s, divides by Δ and reads the slot.

Two very different errors appear. The encryption noise is tiny, around one millionth, and controlled by Δ. The approximation error is much larger and comes from replacing ReLU with a polynomial. In CKKS, getting the non-linear layers right matters more for accuracy than the encryption itself.
